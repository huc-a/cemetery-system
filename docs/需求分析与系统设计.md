# 智慧墓园管理系统 — 需求分析与系统设计

> 项目：青松陵园 · 智慧墓园管理系统（Spring Boot 3.3.5 + Vue 3 + MySQL 8）
> 调研日期：2026-11-12。调研来源：舜和智慧殡葬/公墓管理系统、陵管家智慧园区平台、福寿园「云祭扫」、各地民政云祭扫实践（温州智慧墓园、南京雨花功德园、西安凤栖山人文纪念园等）及行业评析文章。

## 一、行业调研要点

1. **行业主流程是一条线**：看墓选墓 → 预订锁位 → 签约购墓 → 缴费 → 安葬（落葬） → 碑刻/瓷像 → 祭扫服务 → 管理费续缴 → 巡查养护。优秀系统（如舜和旗舰版）的核心卖点是"一墓一档"：一笔业务从登记、结算到线上缴费在同一流程内闭环，不靠人工导表对表。
2. **墓位可视化是标配**：GIS/网格平面图实时显示墓位状态（空闲/预留/已售/已葬/维护），支持平板现场选墓、网格与列表两模式、扫码定位导航。
3. **管理费续费是最耗人力的环节**：合同制管理费按年收取（如20年一缴或分期），系统需到期自动提醒、逾期催缴、线上续缴并顺延周期；寄存格位续费同理。
4. **清明等高峰期祭扫实行分时预约限流**：按日期+时段预约、生成凭证、入口核销；多地陵园容量管控明确。
5. **云祭扫/在线纪念馆**：为逝者建线上纪念馆（生平、照片、墓志铭），支持献花、点烛、上香、留言、祭文；纪念馆是"数字墓碑"，可长期保存。
6. **代客祭扫是成熟的付费服务**：套餐明码标价（市场价约35–640元/次：擦碑、献花、供果、点烛、诵祭文），完成后照片/视频回传家属并可评价——必须有完整的下单→派单→执行→回传流转。
7. **增值服务/商品**：立碑、碑文增刻描金、瓷像、绿化养护、墓碑清洗翻新、礼仪服务、鲜花预订、骨灰寄存等可在线下单。
8. **巡查养护与安全**：墓区日常巡查、设施维修、绿化养护、消防/防火巡查（冬季防火、禁止焚烧）形成工单闭环；管理方还需处理墓位报修。
9. **财务**：合同收款可分期；续费、服务收费统一流水，支持按月/季/年汇总与收入构成分析，对账口径一致。
10. **公告通知**：祭扫预约公告、防火提示、收费提醒、施工通知等是园区对家属的主要触达渠道。

## 二、需求分析

### 角色
| 角色 | 说明 | 数据范围 |
|---|---|---|
| ADMIN 管理员 | 园区管理者 | 全部数据、用户管理、财务统计 |
| STAFF 园区工作人员 | 销售/礼仪/养护人员 | 业务数据；服务订单与工单按派单范围 |
| FAMILY 家属/客户 | 购墓与祭扫客户 | 仅本人合同、费用、预约、订单、纪念馆 |

### 功能需求（模块）
1. 墓区管理：分区（传统/艺术/生态/家族/壁葬）档案、起价、售出统计。
2. 墓位管理：区-排-号编码，类型/面积/朝向/价格/管理费年费；状态机 FREE 空闲 / RESERVED 已预订 / SOLD 已售 / BURIED 已安葬 / MAINTENANCE 维护中；支持按排×列批量生成。
3. 可视化选墓：平面网格按状态着色，点击查看详情，在线预订或直接生成购墓合同。
4. 逝者档案：一人一档，生卒、享年自动计算、绑定墓位与家属；建档自动生成在线纪念馆。
5. 家属客户管理：账号即客户档案（姓名/电话/邮箱/住址），启停管理。
6. 购墓合同/订单：选墓→生成合同（总价=墓价+2%综合服务费+管理费×年限）→签约（墓位 RESERVED→SOLD）→缴费（可分次，超额拒绝，未签约拒绝缴费）→缴清自动生成首期管理费周期。已售/已安葬墓位重复购买、已存在有效合同重复购买均拒绝。
7. 管理费与续费：到期日动态状态（已缴/待缴/临期30天/逾期），逾期与临期提醒列表及金额汇总；续缴落财务流水并自动顺延下一周期。
8. 安葬预约与登记：仅已售墓位可预约；同墓位同日同时段冲突拒绝；登记完成墓位 SOLD→BURIED 并回填逝者安葬日期。
9. 祭扫预约：4 个时段/日，每时段容量 20 人，超限拒绝；可查看各时段余量；工作人员核销入园。
10. 云祭扫/在线纪念馆：纪念页（生平、墓志铭），献花/点烛/上香/鞠躬/留言五种动作全部计数落库并形成祭扫时间线。
11. 服务项目与订单：立碑、代祭扫、绿化养护等 10 类服务明码标价；下单→支付→派单→开始→完成（回传说明）流转，非法流转拒绝。
12. 巡查养护工单：巡查/维修/绿化/养护/报修，优先级；派单→处理→完成（结果必填）流转。
13. 收费/财务记录：三类业务统一流水，汇总与仪表盘收入同口径对账。
14. 数据统计仪表盘（ECharts）：墓位状态分布、近6月收入、收入构成、近7天祭扫趋势、各墓区售出率。
15. 通知公告：置顶、分类（公告/安全/收费/服务），游客可见。
16. 系统用户管理：三角色账号 CRUD 与启停。

### 非功能
- JWT 无状态认证 + 角色数据隔离；家属端仅能访问本人数据（接口层过滤+校验）。
- 游客可浏览前台（墓区、选墓平面图脱敏、纪念馆墙、服务、公告），敏感操作引导登录。
- 前后端同源部署：前端构建产物由 Spring Boot 静态托管，systemd 单服务运行。

## 三、系统设计

### 技术架构
- 后端：Spring Boot 3.3.5 / Java 21 / Spring Data JPA / Spring Security + JWT(jjwt 0.12.6) / MySQL 8 / springdoc OpenAPI。
- 前端：Vue 3 + Vite 5 + Element Plus + Pinia + Vue Router（Hash）+ ECharts 5 + Axios。
- 布局：家属前台（顶部导航，墨绿+金色）与管理后台（侧边栏）双布局，按角色路由分流；登录双入口（家属入口 /login、员工入口 /admin/login，交叉登录拦截并提示）。

### 数据库（cemetery_db，15 张表）
sys_user 系统用户、cemetery_area 墓区、grave_plot 墓位、deceased 逝者档案、purchase_contract 购墓合同、management_fee 管理费、burial_record 安葬记录、visit_appointment 祭扫预约、memorial_hall 纪念馆、memorial_action 祭扫动作、service_product 服务项目、service_order 服务订单、work_order 巡查工单、payment_record 财务流水、notice 公告。

### 核心业务规则
- 墓位状态机与合同联动（见模块 6）；管理费状态不落静态值、按 dueDate 动态计算，避免过期状态失真。
- 祭扫容量：count(visitDate+slot, status≠CANCELLED) + 本次人数 > 20 → 拒绝。
- 云祭扫计数与动作流水同事务写入，保证计数与时间线一致。
- 所有收费动作（合同缴费/管理费续缴/服务支付）统一写入 payment_record，统计接口直接以流水汇总，确保与 DB 对账一致。

### 部署
- systemd 服务 cemetery-app，端口 8083（端口注册表：8080 宠物、8081 宿舍、8083 本系统）；公网域名 8083.453.de5.net 由用户在 Cloudflare 配置路由指向 localhost:8083。
- 数据库账号 cemetery，密码仅存于项目 .env（0600）。

## 四、种子数据规模
5 个墓区、122 个墓位、12 位用户（1 管理员+3 工作人员+8 家属）、10 位逝者、12 份合同、14 笔管理费（含逾期2/临期2）、7 条安葬记录、6 条祭扫预约、10 座纪念馆、10 个服务项目、6 笔服务订单、7 张工单、16+ 笔财务流水、5 条公告。
